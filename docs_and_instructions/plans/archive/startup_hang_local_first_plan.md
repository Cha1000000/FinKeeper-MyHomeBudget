# План: бесконечная загрузка при старте на «зависающей» сети (local-first старт)

Статус: **реализовано** — `0179cec` (+ доработки `6859304`, см. `startup_hang_followups_plan.md`).
Перепроверен по коду и исходникам/байткоду Ktor 3.6.0 и OkHttp 5.5.0 (02.10, вторая сессия) —
выводы разделов 2–3 подтвердились, найденные усилители — в разделе 3а.
Дата расследования: 02.10.2026. Ktor Client 3.6.0, Kotlin 2.4.20.

## 1. Симптом

На мобильном интернете (два оператора, 30.09 и 01.10) приложение висит на Splash / LoadingScreen,
Wi-Fi работает, веб-версия в те же моменты тоже не открывалась. Версия причины: «белые списки» —
пакеты к `157.22.172.217` молча теряются (DROP), соединение не отклоняется, а зависает.

## 2. Что показало расследование

Таймауты в клиенте **конечные** (`ApiClient.kt:32-42`: `requestTimeout=30 с`, `connectTimeout=10 с`),
бесконечного ожидания нет. Проблема в другом: UI **последовательно** ждёт цепочку сетевых вызовов,
прежде чем показать локальные данные, а ошибки внутри цепочки глотаются, поэтому цепочка не
прерывается после первой неудачи.

Замеры на стенде (`SYN`-тишина, адрес без ответа, настоящий клиент Ktor 3.6.0 / OkHttp с теми же настройками):

| Сценарий | Замер |
|---|---|
| Один вызов, SYN-тишина | 10,7 с (connectTimeout) |
| Один вызов, TLS молчит после TCP | 10,1 с (дефолт OkHttp socket 10 с) |
| Один вызов, сервер «капает» ответ | 30,0 с (requestTimeout) |
| `checkAuth` = `withRetry(3){getMe}`, SYN-тишина | **31,7 с** |
| Dashboard до `isLoading=false`, SYN-тишина | **101,8 с** |

Плюс Splash минимум 2 с (`App.kt:49-57`). То есть при тишине пользователь видит экран загрузки
**≈ 2 мин** (авторизация ≈ 32 с, затем Dashboard ≈ 102 с), в худшем случае (каждый вызов добирает
до 30 с) — до **≈ 6 мин**. «Бесконечной» загрузка кажется именно из-за этого.

## 3. Корневые причины

1. **Splash ждёт сеть.** `AuthState.isLoading = true` по умолчанию (`AuthViewModel.kt:25`),
   снимается только после `getMe` с 3 попытками (`AuthViewModel.kt:90-96`); офлайн-режим
   (`AuthViewModel.kt:125-137`) включается лишь после исчерпания попыток.
2. **Dashboard: сеть → Room.** В `loadDataSuspend` (`DashboardViewModel.kt:149-306`) сначала фаза 1
   (сеть, 164-193), потом чтение локальной БД (фаза 2), потом ещё `getCumulativeBalance` ×2
   (`:246-248`) — и только потом `isLoading=false` (`:281`).
3. **Нет short-circuit.** `syncWithServer` в репозиториях возвращает `Result` и глотает исключения,
   поэтому `try` в `:170-193` не срабатывает, и цепочка из ≈10 вызовов выполняется целиком,
   каждый раз заново упираясь в таймаут.
4. **`withRetry` ретраит любой `Throwable`**, включая таймауты (`util/Retry.kt`), — умножает ожидание.
5. **Тот же паттерн** в `MonthViewModel` (~222-231), `SavingsViewModel` (~89), `CategoriesViewModel` (~94/106).
6. **`NetworkMonitor` не помогает.** Android: `NET_CAPABILITY_INTERNET` без `VALIDATED`
   (`androidMain/.../NetworkMonitor.kt`), на «белых списках» сеть «есть» → `isOnline=true`.
   Десктоп: HEAD-запрос к `app.finkeeper24.ru` раз в 10 с, таймаут 3 с — работает как индикатор.

Sync (`SyncManager.syncAll`, `SyncService`) запускается в фоне и UI не блокирует — это не причина.
Но VM делают собственную сеть до Room параллельно с ним.

## 3а. Дополнения после перепроверки

Проверено по коду; влияние на время (кроме п. 1) **не замерялось**.

1. **Повторный полноэкранный лоадер на каждом входе в «Обзор».** `DashboardScreen.kt:43`
   `LaunchedEffect(Unit) { onRefresh() }` → `AppNavigation.kt:215` `loadData()` с `showLoader = true`
   → `isLoading = true` → `LoadingScreen` (`DashboardScreen.kt:45-48`), даже если данные уже показаны.
   Ушёл на другую вкладку и вернулся — ещё ≈ 100 с лоадера. Именно это делает загрузку
   «бесконечной» в глазах пользователя.
2. **Общие `Mutex` у репозиториев.** Репозитории — `single` в Koin (`di/AppModule.kt:50-58`),
   `syncPullMutex` у каждого свой, но общий для всех вызывающих. На старте один и тот же
   `categoryRepository.syncWithServer` зовут `SyncManager.syncFromServer` (`SyncManager.kt:270`),
   `MonthViewModel` (`:222`), `CategoriesViewModel` (`:94`) и `DashboardViewModel` (`:172`) — они
   встают в очередь, и каждый ждёт таймауты остальных. Фоновый sync UI напрямую не блокирует,
   но через мьютексы удлиняет фазу 1 Dashboard.
3. **Лимит OkHttp — 5 одновременных запросов на хост.** Ktor вызывает `call.enqueue`
   (`ktor-client-okhttp OkUtils.kt:36`), `Dispatcher.maxRequestsPerHost = 5` (байткод OkHttp 5.5.0).
   После входа параллельно идут цепочки Dashboard, Month, Categories, `Settings.loadBackups`
   (`withRetry(3)`), `SyncManager`, `loadSocialProviders`. Сверх пяти запрос ждёт в очереди
   Dispatcher, и его отрезает уже `requestTimeout` 30 с, а не connect 10 с.
4. **Новый месяц — лишний вызов.** `MonthRepository.getOrCreateMonth` (`:54-61`, `:84-89`) при
   `serverId == null` синхронно зовёт `ensureMonth` (+10 с). 01.10 — первый день месяца, ровно
   этот случай. Совпадение, не причина.
5. **`withRetry` ловит `Throwable`, включая `CancellationException`** (`Retry.kt:21`): отменённую
   корутину он «повторяет» вместо немедленного выхода. На время старта почти не влияет,
   но чинить заодно.

### Худший случай по коду (Android, OkHttp 5.5.0)

`T` — цена одного вызова: 10 с при SYN-тишине (`connectTimeout`) и при молчащем TLS
(`readTimeout` OkHttp по умолчанию 10 с, `socketTimeoutMillis` не задан); 30 с, если сервер
«капает» ответ или запрос стоит в очереди Dispatcher (`requestTimeout`).

| Этап | Где | Вызовы | T = 10 с | T = 30 с |
|---|---|---|---|---|
| Splash | `AuthViewModel.kt:88-96`, `App.kt:49-57` | `getMe` × 3 + пауза 0,3 + 0,6 с | ≈ 31 с | ≈ 91 с |
| Месяц | `MonthRepository.kt:54-61` | `ensureMonth`, только если нет `serverId` | 0–10 с | 0–30 с |
| Фаза 1 | `DashboardViewModel.kt:170-193` | 6 pull + `summary` × 2 (исключение → `trend` пропущен) | ≈ 80 с | ≈ 240 с |
| Баланс | `DashboardViewModel.kt:245-252` | `getCumulativeBalance` × 2 | ≈ 20 с | ≈ 60 с |
| **До данных из Room** | | | **≈ 2 мин 10 с** | **≈ 6,5 мин** |
| Каждый возврат на «Обзор» | `DashboardScreen.kt:43-48` | вся цепочка заново | ≈ 100 с | ≈ 5 мин |

Плюс ожидание на мьютексах (п. 2) — не посчитано. Расчёт для T = 10 с сходится с замером
на стенде из раздела 2 (101,8 с на Dashboard).

**Десктоп** (CIO): общий `commonMain`, цепочка та же. `connectTimeout` 10 с берётся из плагина,
`socketTimeout` у CIO по умолчанию бесконечный (`CIOEngineConfig.kt:127`), собственный
`requestTimeout` движка (15 с) при установленном `HttpTimeout` отключается (`Endpoint.kt:347-363`).
Значит, молчащий TLS на десктопе стоит 30 с на вызов, а не 10.

## 4. Предложение (рекомендуется вариант Б)

Принцип: **Room показываем сразу, сервер подтягиваем в фоне**, ожидание ограничено бюджетом.

1. **Старт без блокировки на сети.** Если в `tokenStorage` есть токен и `userId` — сразу
   `isAuthenticated=true` с локальным пользователем; `getMe` уходит в фон: обновляет профиль,
   на `401/403` выполняет логаут (как сейчас). Splash — только фиксированные 2 с.
2. **Dashboard: порядок «Room → сеть».** Сначала фаза 2 (локальная БД) и `isLoading=false`,
   `cumulativeBalance` — сразу локальный fallback. Затем фаза 1 в фоне; по завершении — повторное
   чтение Room и точное значение баланса. Тот же приём в Month/Savings/Categories.
3. **Бюджет и short-circuit для сети на старте.** Один общий `withTimeout(≈20 с)` на фазу 1;
   после первой сетевой ошибки типа timeout/connect остальные вызовы фазы пропускаются,
   `isOffline=true`.
4. **`withRetry`: не ретраить таймауты и connect-ошибки на старте** (ретраи оставить для 5xx/сброса
   соединения). Явный `socketTimeoutMillis` в `HttpTimeout` (≈15 с), чтобы CIO на десктопе
   не зависел от «бесконечного» дефолта.
5. **Статус.** Ненавязчивый баннер «Нет связи с сервером, показаны сохранённые данные»
   (строка в ресурсы, не хардкод) с кнопкой «Повторить»; при восстановлении — автообновление.
6. **Не показывать полноэкранный лоадер, если данные уже есть.** `loadData(showLoader)` —
   `showLoader` только при пустом состоянии; при возврате на вкладку — тихое обновление
   (`isRefreshing`). Так же в Month/Savings/Categories.
7. **`withRetry`: `CancellationException` пробрасывать сразу.**
8. **Тесты:** юнит-тесты на «зависающий» клиент (MockEngine с `delay`) — время до первых данных
   < 3 с; Dashboard получает данные из Room до ответа сервера; ручная проверка на эмуляторе
   с «чёрной дырой» (iptables DROP на адрес сервера, **не** режим самолёта).

## 5. Альтернативы

| Вариант | + | − |
|---|---|---|
| А. Только урезать таймауты (connect 5 с, request 10 с) | Минимум правок | Лечит симптом: цепочка ×10 всё равно ≈ 50 с; ложные отказы на медленной сети |
| **Б. Local-first + бюджет + short-circuit (рекомендую)** | Мгновенный старт при любой сети; соответствует offline-first идеологии приложения; решает все экраны | Больше правок (Auth + 4 VM), нужно аккуратно с повторным чтением Room и гонками |
| В. Health-probe `/health` с коротким таймаутом перед стартом | Быстрое решение «онлайн/офлайн» | Лишний запрос; при DROP тоже ждёт таймаут; сам по себе UI не разблокирует |

## 6. Шаги реализации (после одобрения)

1. Auth: старт без ожидания `getMe` + тест.
2. Retry: исключение для таймаутов/connect + `socketTimeout` + тест.
3. Dashboard: Room → сеть, бюджет, short-circuit + тест.
4. Month / Savings / Categories — тот же паттерн, по одному.
5. Баннер «Нет связи с сервером» + строки в ресурсы; лоадер только при пустом состоянии.
6. Проверка на эмуляторе (DROP) и на десктопе; сборка и тесты зелёные → ревью → ждать «ок» на коммит.

## 7. Не подтверждено запуском

- Поведение при зависшем **DNS** (OkHttp `connectTimeout` его не покрывает — ограничит только
  `requestTimeout` 30 с).
- Порядок вложенности interceptor'а refresh (`ApiClient.kt`, `plugin(HttpSend).intercept`) и
  `HttpTimeout`: верхняя граница ~30 с на один вызов вероятна, но не измерена.
- CIO на десктопе: по исходникам `socketTimeout` по умолчанию бесконечный
  (`CIOEngineConfig.kt:127`), connect 5 с (`:120`); поведение «молчащий сервер после TCP» —
  ограничено только `requestTimeout`, замером не проверено.
- Реальная причина у операторов (белые списки) — по логам не подтверждена; сервер считается исправным.

# KMP: пополнение копилки офлайн сразу уменьшает «Остаток» лимита трат

Дата: 2026-09-22 · Платформа: KMP (Android / iOS / Desktop) · Выпуск в составе 2.2.3 · Сервер и веб не меняются

## Проблема

Пополнение копилки в KMP (`SavingsViewModel.addTransaction` →
`SavingsTransactionRepository.createTransaction`) локально делает две вещи:
обновляет сумму копилки и создаёт запись `savings_transactions` со статусом `pending`
в очереди синхронизации. Скрытый расход «Пополнение копилки», который уменьшает
лимит, создаёт **только сервер** (`POST /savings_transactions`, при
`amount > 0 && month_id`).

Отсюда две ошибки.

**A. Офлайн остаток не уменьшается.** Пока пополнение не выгружено на сервер,
«Остаток» в «Месяце» (и «Лимит на расходы» в «Обзоре» офлайн) не меняется.
Пользователь решит, что это глюк, пополнит ещё раз, и копилка задвоится.

**B. Скрытый расход может не появиться совсем.** При выгрузке пополнения
(`SyncManager.syncSavingsTransactionToServer`, строки 1045 и 1070) месяц
сопоставляется только по уже известному `serverId`. Если месяц создан офлайн
(например, первое пополнение в новом месяце без сети), на сервер уйдёт
`month_id = null`, и сервер не создаст скрытый расход **никогда**: лимит не
уменьшится даже после синхронизации. Доходы и расходы в той же ситуации
вызывают `resolveMonthServerId` (создаёт/получает месяц через `ensureMonth`),
а если не вышло — бросают исключение, и очередь повторяет позже.

## Решение

### A. Учитывать ещё не выгруженные пополнения в расчёте

Скрытый расход локально **не создаём**: после синхронизации сервер пришлёт свой,
и получится дубль. Вместо этого при расчёте «всех расходов месяца» прибавляем
пополнения этого месяца, которые ещё не ушли на сервер:

```
все расходы месяца = локальные расходы (вкл. скрытые, уже пришедшие с сервера)
                   + Σ пополнений копилок этого месяца с sync_status ≠ 'synced' и amount > 0
```

Когда пополнение выгружено, его статус становится `synced`, и оно перестаёт
учитываться. Его место занимает скрытый расход с сервера (приходит при следующей
синхронизации расходов). Снятия (`amount < 0`) не считаем — сервер для них
скрытый расход не создаёт.

Изменения:

1. **`data/repository/savings/UnsyncedDeposits.kt`** (новый, чистая функция):
   `fun unsyncedDepositsTotal(transactions: List<SavingsTransaction>, monthLocalId: Long): Double` —
   фильтр по `monthId == monthLocalId`, `syncStatus != SYNCED`, `amount > 0`, сумма.
2. **`SavingsTransactionRepository`** — `suspend fun getUnsyncedDepositsTotal(userId, monthLocalId): Double`
   через `savingsTransactionDao.getAllByUser(userId)` + функция из п.1. Новый SQL-запрос
   и миграция не нужны.
3. **`MonthViewModel`** — новая зависимость `SavingsTransactionRepository`;
   `totalAllExpenses = allExpenses.sum + unsyncedDeposits`. Плашка, прогресс-бар,
   «X / Y» и разбивка в подсказке «Как считается лимит» подхватят это
   автоматически (разбивка считает пополнения как `totalAllExpenses − totalExpense`).
4. **`DashboardViewModel`** — то же: `totalAllExpense = (summary?.expenses ?: локальная сумма) + unsyncedDeposits`.
   Отсюда же считаются «Лимит на расходы» и «Прогноз: свободно».
5. **`di/AppModule.kt`** — добавить `get()` в фабрики `MonthViewModel` и `DashboardViewModel`.

«Месяц» перечитывает данные при каждом открытии экрана (`LaunchedEffect(Unit) { onRefresh() }`),
поэтому после пополнения в «Копилках» и возврата в «Месяц» остаток сразу будет новым.

### B. Всегда передавать месяц при выгрузке пополнения

**`SyncManager.syncSavingsTransactionToServer`** (INSERT и UPDATE): вместо
чтения `serverId` вызывать `resolveMonthServerId(localMonthId)`. Если у пополнения
есть месяц, а разрешить его не удалось — бросить `IllegalStateException`, как
в выгрузке расходов (строки 678–684). Очередь повторит позже, и пополнение не уйдёт
без месяца.

### C. Десктоп: миграция стирала month_id при каждом запуске (найдено при проверке)

`desktopMain/.../DatabaseDriverFactory.kt` пересобирал `savings_transactions` на **каждом**
старте и не копировал `month_id` (с 2026-02-17, коммит `d33f38f`). Офлайн-пополнение,
пережившее перезапуск, уходило на сервер без месяца, и фикс B этого не ловил.
Теперь: `migrateSavingsTransactionsMonthColumn` проверяет `PRAGMA table_info` и пересобирает
таблицу, только если `month_id` не 4-я колонка; `month_id` переносится; вся пересборка идёт
одной транзакцией (при сбое — ROLLBACK, данные целы). Тесты: `SavingsTransactionsMigrationTest`.

### D. Доработки по ревью

- После выгрузки пополнений (`syncAll` и `scheduleProcessQueue`) сразу скачиваются расходы
  их месяцев (`pullHiddenSavingsExpenses`), и только потом шлётся `dataUpdated`. Иначе «Месяц»
  (перечитывает только локальную БД) показал бы остаток без пополнения до следующей синхронизации.
- Месяц на сервере обязателен только для пополнений (`amount > 0`); снятия его не ждут.

### Прод: пополнения без месяца (проверено только чтением, 2026-09-22)

13 записей на 141 200 ₽, все — Владимира, все 17.02.2026 06:36–08:46 (день появления
`month_id`), похоже на тестовые пополнения/снятия. У других пользователей нет. Решение о
правке задним числом — за Владимиром.

## Пограничные случаи (осознанно принимаем)

- **Короткое окно двойного счёта.** Выгрузка пополнения и скачивание расходов
  защищены разными мьютексами. Если экран загрузится ровно между «сервер создал
  скрытый расход» и «локально отмечено `synced`» (миллисекунды), пополнение
  посчитается дважды — до следующего открытия экрана. То же, если ответ сервера
  потерялся в сети: запись останется `pending`, а скрытый расход уже придёт. При
  повторной выгрузке (идемпотентный `operationId`) статус станет `synced`, и всё
  выровняется само. Сопоставлять пополнения со скрытыми расходами по сумме и дате
  не стал: эвристика ошибается на двух одинаковых пополнениях в один день.
- **`failed`-пополнения** считаются: локально копилка уже показана пополненной,
  и остаток должен быть с ней согласован.

## Проверка

1. **Unit-тест (commonTest)** для `unsyncedDepositsTotal`: учитываются только свой
   месяц, не-`synced` и `amount > 0`; снятия, чужой месяц и `synced` — нет.
   Сначала тест (падает), потом функция.
2. Все unit- и desktop-тесты — зелёные.
3. **Desktop-песочница** (`FINKEEPER_USER_HOME`) + локальный сервер с временной БД:
   - онлайн: зайти, запомнить «Остаток»;
   - остановить сервер (офлайн), пополнить копилку на 1 000 ₽ → «Остаток» в «Месяце»
     и «Лимит на расходы» в «Обзоре» сразу уменьшились на 1 000, в подсказке
     «Пополнения копилок» выросли на 1 000;
   - запустить сервер, дождаться синхронизации → цифры **не изменились** (нет дубля),
     на сервере в summary есть скрытый расход;
   - **ошибка B:** при закрытом приложении обнулить `server_id` текущего месяца
     в песочной БД, офлайн пополнить, включить сервер → на сервере у пополнения
     есть `month_id` и создан скрытый расход.
4. Ревью `kotlin-reviewer`, затем релизная сборка 2.2.3 на телефон — проверка
   в режиме полёта.

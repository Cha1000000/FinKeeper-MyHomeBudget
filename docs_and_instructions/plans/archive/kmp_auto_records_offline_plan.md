# KMP: регулярные записи (автоплатежи/автопоступления) — онлайн и офлайн без сюрпризов

Дата: 2026-09-22 · Платформа: KMP (Android / iOS / Desktop) · Выпуск в составе 2.2.3 · Сервер и веб не меняются

**Критерий приёмки (Володя):** переходы онлайн ↔ офлайн, включая смену месяца без сети,
для пользователя незаметны — никаких скачков сумм и сюрпризов при синхронизации.

## Как устроено сейчас

Фиксированная категория/источник без «требует подтверждения» (`require_confirm = 0`) с днём
`auto_day` — шаблон регулярной записи. Реальную запись создаёт **только сервер**
(`autoCreateRecurringRecords` → расход с комментарием «Регулярный платёж» или доход с
источником = имя шаблона, дата = день месяца, сумма = override ?: fixed) и фиксирует это в
`auto_created_records`. Запускается это **только** из `POST /months/ensure`.

KMP показывает план через `PlannedCalculator` (оффлайн), исключая уже созданные записи
(`materializedKeys` ← локальное зеркало `auto_created_records`, приходит в `planned-state`).
Запись, у которой **наступил день**, из плана выкидывается (`PlannedCalculator.kt:110–111`) в
расчёте, что сервер её уже создал.

## Проблемы (подтверждены кодом и экспериментом в песочнице)

1. **Онлайн, только KMP — записи не создаются вообще.** KMP вызывает `ensureMonth` лишь пока у
   месяца нет `serverId` (`MonthRepository.getOrCreateMonth`, `SyncManager.resolveMonthServerId`,
   `PlannedRepository.resolveServerMonthId`). Для уже известного месяца — никогда. Эксперимент:
   фикс. категория с днём 22, месяц создан раньше → после полной синхронизации KMP на сервере
   нет ни `auto_created`, ни расхода; ручной `ensure` (как у веба) — сразу создаёт. У Володи
   маскировалось веб-версией (она зовёт `ensure` при каждой загрузке).
2. **Офлайн — запись исчезает**, пока сервер её не создал и она не пришла синхронизацией:
   нет ни в плане, ни в расходах/доходах, лимит и прогноз «забывают» её, потом скачок.
   Касается и **доходов** (например, зарплаты по расписанию), и **прошлого месяца** при
   смене месяца офлайн.

## Решение

### 1. Онлайн: KMP запускает создание регулярных записей, как веб

`MonthRepository.ensureOnServer(monthLocalId)` — вызывает `apiClient.ensureMonth(year, month)`
(идемпотентно на сервере), обновляет `serverId`. Вызывается **перед** скачиванием доходов,
расходов и план-слоя во всех трёх путях синхронизации месяца:
`MonthViewModel` (фаза 1), `DashboardViewModel` (фаза 1), `SyncManager.syncFromServer`.
Ошибка сети не прерывает загрузку (как и сейчас для остальных запросов фазы 1).

### 2. Пока запись не пришла с сервера — «отмечена автоматически» (виртуально)

`PlannedCalculator.calculate` вместо того, чтобы выкидывать наступившие регулярные записи,
возвращает их отдельным списком `autoApplied` (правило: `require_confirm = 0`, не пропущена,
день наступил — для текущего месяца `dueDay <= today`, для прошлого — всегда; и **нет** в
`materializedKeys`). Сумма = override ?: fixed, дата = день месяца — ровно как создаст сервер.

`MonthViewModel` / `DashboardViewModel` добавляют `autoApplied` к фактическим записям:
- расходы → в группу своей категории (комментарий «Регулярный платёж»), в `totalExpense`,
  `totalAllExpenses` (лимит, «Остаток», подсказка «Как считается лимит»), разбивку «Обзора»;
- доходы → в список доходов (источник = имя шаблона), в `totalIncome`;
- в прогнозе они уже как факт, не как план (план их не содержит) — прогноз не меняется.

Когда сервер создаст запись и она придёт (вместе с `auto_created` в том же проходе
синхронизации: доходы → расходы → план-слой), ключ попадёт в `materializedKeys`, виртуальная
запись исчезнет, а на её месте окажется настоящая с той же суммой и датой — без скачка.
Обычно при наличии сети (п.1) `autoApplied` пуст.

### 3. UI «Месяца» (вариант 1, согласован)

Виртуальная запись стоит на своём месте как обычная, суммы учтены. Под ней мелкая подпись
**«⏳ отмечено автоматически»**. По нажатию вместо меню «изменить/удалить» — короткий диалог:
- расход: «Регулярный расход «%s» отмечен автоматически по расписанию. Пока нет связи с
  сервером, он хранится только в расчёте — изменить или удалить его можно после синхронизации.»
- доход: «Регулярный доход «%s» отмечен автоматически по расписанию. …» (то же окончание).

Лексика — учётная: «отмечен / учтён», **не** «проведён» (это бухгалтерия, а не банк).
Технически: виртуальные записи получают отрицательные id и перечисляются в
`MonthViewState.autoAppliedExpenseIds / autoAppliedIncomeIds`; экран по ним выбирает подпись
и диалог.

### 4. Доработки по ревью

- Страховка от двойного счёта при частичном сбое (скачались записи, но не `planned-state`):
  `PlannedResult.withoutDownloadedRecords` убирает виртуальную запись, если среди скачанных
  уже есть настоящая того же вида (расход: категория + дата + «Регулярный платёж»; доход:
  источник + дата). Тесты: `AutoAppliedRecordsTest`.
- «Обзор»: если `ensure` в этом цикле прошёл и summary получена с сервера, виртуальные записи
  к итогам не прибавляются (сервер их уже создал и учёл в summary).

## Пограничные случаи

- **Двойной счёт** возможен, только если реальная запись уже скачана, а `auto_created` — ещё
  нет. Все три пути скачивают доходы → расходы → план-слой в одном проходе и пересчитывают
  экран после него, так что окно — только при обрыве сети ровно между этими запросами;
  исправится при следующей синхронизации. (Сопоставлять по сумме/дате не стал — ненадёжно.)
- **Пользователь офлайн изменил сумму шаблона** после наступления дня: виртуальная запись
  покажет новую сумму, сервер при создании возьмёт ту, что будет у него на момент `ensure`
  (шаблон к тому времени уже синхронизирован) — совпадут.
- **Прошлые месяцы, которые никто не открыл онлайн:** сервер создаёт записи только при
  `ensure` конкретного месяца — и у веба так же. В KMP прошлый месяц при открытии онлайн
  получит `ensure` (п.1). Серверный «Всего активов» по неоткрытым месяцам — существующее
  поведение, вне рамок.

## Проверка

1. Unit-тесты `PlannedCalculatorTest`: наступившая регулярная запись без `materialized` →
   в `autoApplied` (не в плане); с `materialized` → нигде; `require_confirm` и пропущенные →
   не в `autoApplied`; прошлый месяц; доходы.
2. Все unit/desktop-тесты зелёные.
3. Песочница + локальный сервер:
   - **онлайн**: фикс. категория с днём = сегодня, месяц создан раньше → после загрузки
     «Месяца» на сервере есть `auto_created` и расход, в KMP — настоящая запись;
   - **офлайн**: то же при выключенном сервере → запись видна с подписью «⏳ отмечено
     автоматически», учтена в расходах/лимите/«Обзоре»; нажатие — диалог; включить сервер →
     запись та же, подпись пропала, суммы **не изменились**;
   - то же для **дохода**.
4. Ревью `kotlin-reviewer`, релиз на телефон.

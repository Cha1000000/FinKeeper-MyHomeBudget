# План техдолга (с приоритетами)

## Цели
- Повысить безопасность (секреты, аутентификация).
- Снизить риск повреждения/рассогласования данных.
- Упростить сопровождение и развитие функционала.
- Сделать систему устойчивой к изменениям схемы и регрессиям.

## Принципы приоритизации
- P0: риски безопасности и потери данных.
- P1: риски корректности бизнес‑логики и аналитики.
- P2: качество поддержки/масштабируемость.
- P3: улучшения удобства разработки.

## Приоритет P0 (срочно)
1. Перенести JWT‑секрет и конфигурацию в `.env`
   - Причина: жестко заданный секрет в коде.
   - Затронутые файлы: `server/index.js`, `DEPLOYMENT.md`.
   - Шаги:
     - Добавить `dotenv` и загрузку конфигов (уже есть в зависимостях).
     - Вынести `JWT_SECRET`, `PORT` в переменные окружения.
     - Обновить документацию и пример `.env`.
   - Критерий готовности: запуск работает с `.env`, секрет не хранится в коде.

2. Единый источник конфигурации портов
   - Причина: расхождение портов между сервером, Vite и документацией.
   - Затронутые файлы: `server/index.js`, `client/vite.config.ts`, `DEPLOYMENT.md`.
   - Шаги:
     - Вынести порт API в `.env` для сервера.
     - В `vite.config.ts` использовать `process.env` (через `loadEnv`).
     - Синхронизировать документирование.
   - Критерий готовности: смена порта в `.env` меняет и прокси, и сервер.

## Приоритет P1 (высокий)
3. Формальная валидация входных данных API
   - Причина: минимальная проверка входных данных.
   - Затронутые файлы: `server/index.js`.
   - Шаги:
     - Ввести схему валидации (например, Zod/Joi).
     - Валидировать `amount`, `date`, `month_id`, `category_id`, `name`.
   - Критерий готовности: корректные HTTP 400 с описанием ошибок.

4. Улучшение логики копилок (исключение “скрытых расходов”)
   - Причина: “магическая” категория и дублирование смысла в `expenses`.
   - Затронутые файлы: `server/index.js`, `client/src/pages/Dashboard.tsx`, `client/src/pages/MonthView.tsx`.
   - Шаги:
     - Рассмотреть выделение накоплений в отдельную модель отчета.
     - Исключить необходимость создавать скрытый расход при пополнении.
     - Пересчитать аналитические формулы.
   - Критерий готовности: накопления учитываются без “скрытых” расходов.

5. Версионирование бэкапов
   - Причина: риск некорректного восстановления при изменении схемы.
   - Затронутые файлы: `server/index.js`, `server/db_setup.js`.
   - Шаги:
     - Ввести поле `schema_version` в `user_backups`.
     - При восстановлении проверять версию и мигрировать.
   - Критерий готовности: старые бэкапы восстанавливаются или отклоняются с явной причиной.

## Приоритет P2 (средний)
6. Каскадные удаления или транзакционные операции удаления
   - Причина: сложные каскады удаления в restore.
   - Шаги:
     - Включить `ON DELETE CASCADE` или реализовать единый транзакционный helper.
   - Критерий готовности: единый контролируемый путь очистки пользовательских данных.

7. Логи и обработка ошибок
   - Причина: ошибки логируются в консоль без структуры.
   - Шаги:
     - Добавить централизованный логгер (минимально: лог‑middleware).
   - Критерий готовности: ошибки API логируются с контекстом.

8. Стабильные вычисления аналитики
   - Причина: расчеты по разным таблицам, риск расхождений.
   - Шаги:
     - Вынести расчеты в отдельные функции/модули.
     - Покрыть несколькими тестовыми сценариями.
   - Критерий готовности: единый модуль расчетов.

## Приоритет P3 (низкий)
9. Тесты (базовый набор)
   - Причина: отсутствие тестов.
   - Шаги:
     - Начать с API smoke‑tests (Auth, CRUD, budgets, savings).
     - Минимальные компонентные тесты для ключевых страниц.
   - Критерий готовности: зеленые тесты на CI и локально.

## Рекомендуемый порядок работ (итерации)
1. P0: секреты + конфиги портов.
2. P1: валидация API + версия бэкапов.
3. P1: пересмотр логики копилок и аналитики.
4. P2: каскадные удаления + логирование.
5. P3: тесты + типизация.
